# Как показать CI JobMatch на лабораторной

Материал к [задаче backend#5](https://github.com/CODEXSQUAD/jobmatch-backend/issues/5). Демонстрация занимает примерно 5–7 минут. Подготовлены два независимых workflow: в backend и frontend.

## Короткое объяснение своими словами

> Мы настроили непрерывную интеграцию — CI. Когда участник открывает или обновляет pull request в main, GitHub автоматически получает код, устанавливает нужные инструменты и зависимости, собирает проект и запускает тесты. Это помогает обнаружить проблемы до объединения изменений. После обновления main проверка повторяется. У frontend и backend отдельные репозитории, поэтому в каждом свой workflow. Результат и причина ошибки доступны всей команде в GitHub.

## Подготовка до занятия

1. В каждом репозитории вручную создайте PR: **base: main**, **compare: feature/ci-build**. В обоих описаниях укажите `Related to https://github.com/CODEXSQUAD/jobmatch-backend/issues/5` и, после создания, ссылку на второй PR. Не закрывайте общую задачу раньше приёмки обеих частей.
2. Дождитесь завершения проверок. В frontend ожидается **Frontend build / Build and test frontend**, в backend — **Backend build / Build and test backend**.
3. Откройте заранее оба PR, их вкладки **Checks**, workflow-файлы и журналы успешных запусков. Запишите ссылки на запуски и SHA проверенных коммитов; сохраните скриншоты на случай проблем с интернетом.
4. Для локального показа нужны Node.js 24 с npm 11/12 и .NET SDK, совместимый с `global.json`. Docker и PostgreSQL для этих тестов не нужны.

**Простой push в feature/ci-build без открытого PR не запускает текущие workflow.** В `push` выбран только `main`; первый запуск ожидается при создании PR в `main`. Кнопка **Run workflow** не предусмотрена: событие `workflow_dispatch` не добавлено. Если PR ещё не создан, показывайте файлы и локальные проверки и прямо говорите, что запуск на GitHub пока не подтверждён. Правила событий описаны в [документации GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).

## Сценарий демонстрации

### 1. Задача и результат — 30 секунд

Покажите issue #5 и объясните: «Задача — автоматически проверять, что изменения frontend и backend собираются и проходят существующие тесты. Результат — по одному файлу `.github/workflows/build.yml` в каждом репозитории и инструкции в README».

### 2. Workflow — 1–2 минуты

Откройте [backend workflow](../.github/workflows/build.yml), затем аналогичный файл frontend. Объясняйте блоки сверху вниз:

| Блок | Что сказать |
|---|---|
| `on` | Проверка запускается на PR, направленный в main, и на обновление main. |
| `permissions: contents: read` | Для получения кода достаточно чтения. Workflow не нужны персональные токены. |
| `concurrency` | Новый запуск отменяет устаревшую проверку того же PR или ветки. |
| `runs-on: ubuntu-24.04` | Команды выполняет runner GitHub на Ubuntu, независимо от компьютера разработчика. |
| `timeout-minutes: 15` | Зависшая проверка ограничена по времени. |
| `Checkout` | Получает код, который нужно проверить. |
| `Setup Node.js` / `Setup .NET` | Читает версию из `.nvmrc` или `global.json`, чтобы CI соответствовал проекту. |
| `uses: ...@SHA` | Версия внешнего Action закреплена по конкретному коммиту. |
| `run` | Выполняет обычные команды установки, сборки и тестов. |

На frontend дополнительно покажите `package-lock.json`: `npm ci` использует lock-файл и проверяет его согласованность с `package.json`. Кэш npm ускоряет повторные загрузки; установка всё равно выполняется.

### 3. Команды и смысл проверок — 1 минута

| Frontend | Backend |
|---|---|
| `npm ci`: установить зависимости по lock-файлу | `dotnet restore JobMatch.slnx`: восстановить NuGet-зависимости |
| `npm run build`: проверить TypeScript и собрать сайт в dist | `dotnet build JobMatch.slnx --configuration Release --no-restore`: собрать весь solution |
| `npm test`: выполнить Vitest без режима ожидания изменений | `dotnet test JobMatch.slnx --configuration Release --no-build --no-restore`: проверить уже собранные проекты |

Frontend тестирует API-клиент: корректные ответы, HTTP- и сетевые ошибки, тайм-аут, отмену запросов и неверный формат ответа. Backend проверяет каталог, повторяемость seed, HTTP-контракт и OpenAPI. Существующие тесты подключены к CI, новые бизнес-сценарии в этой задаче не реализовывались.

### 4. Реальный результат на GitHub — 1–2 минуты

Откройте **Checks** в PR. Покажите проверенный коммит, итоговый статус, затем раскройте шаги сборки и тестов. В журнале frontend видны результат Vite и число тестов, в backend — результат Release-сборки и итог тестового запуска. Повторите для второго репозитория.

Альтернативный путь: вкладка **Actions** репозитория → **Frontend build** или **Backend build** → нужный запуск → job. Обязательно выберите запуск своего PR и последнего коммита. [Справка по журналам GitHub Actions](https://docs.github.com/en/actions/how-tos/monitor-workflows/use-workflow-run-logs).

Скажите: «Если команда завершается с ошибкой, шаг и проверка становятся красными. Разработчик открывает журнал, исправляет код и отправляет новый коммит. GitHub повторяет проверку автоматически».

Не нужно специально ломать рабочую ветку ради демонстрации. Если преподавателю нужен пример сбоя, его можно отдельно подготовить в учебном PR, показать красную проверку и затем исправление. Это не выполненный шаг данной задачи.

## Локальный показ, если GitHub недоступен

В терминалах, открытых в корнях соответствующих **CI-рабочих копий**, выполните:

Frontend:

```bash
git branch --show-current
node --version
npm --version
npm ci
npm run build
npm test
```

Backend:

```bash
git branch --show-current
dotnet --version
dotnet restore JobMatch.slnx
dotnet build JobMatch.slnx --configuration Release --no-restore
dotnet test JobMatch.slnx --configuration Release --no-build --no-restore
```

Для этой задачи ожидается ветка `feature/ci-build`. На компьютере, где готовились изменения, CI-рабочие копии находятся в `.ci-worktrees/jobmatch-frontend` и `.ci-worktrees/jobmatch-backend` относительно общей папки JobMatch. Основные папки сохранены для отдельной задачи Docker Compose. При обычном клонировании достаточно получить ветку CI в своём репозитории.

Если нет интернета и зависимости ещё не установлены, чистая установка может не выполниться. Используйте заранее сохранённый журнал и укажите, когда он был получен. Локальная проверка подтверждает выполнение команд на текущем компьютере; она не доказывает запуск GitHub Actions на Linux.

## Ответы на возможные вопросы

**Почему два workflow?** Frontend и backend живут в отдельных репозиториях. Каждый PR проверяет свой проект; это не общий интеграционный запуск приложения.

**Чем сборка отличается от тестов?** Сборка проверяет возможность получить приложение из исходников. Тесты проверяют конкретное поведение. Успешная сборка сама по себе не означает корректную бизнес-логику.

**Почему не запускается PostgreSQL?** Текущие backend-тесты используют EF Core InMemory и тестовый HTTP-сервер; там, где нужно, каталог подменяется. Они не проверяют настоящие SQL-запросы, миграции и сохранность данных. Эти проверки относятся к интеграции с PostgreSQL и задаче Compose.

**Почему не нужны секреты?** Код и зависимости доступны без персональных учётных данных, подключение к внешней БД отсутствует. GitHub предоставляет служебный токен workflow с ограниченными правами; вручную добавлять персональный токен не нужно.

**Зелёная проверка запрещает объединять плохой код?** Она сообщает результат. Обязательное прохождение перед merge задаётся правилами ветки отдельно. В этой задаче такие правила не настраивались; ревью тоже остаётся необходимым.

**Это CI/CD?** Реализована часть CI: сборка и тесты. Автоматического развёртывания приложения нет.

**Что делать при красной проверке?** Открыть первый упавший шаг и найти причину в журнале. Исправление отправить новым коммитом. При временном сбое загрузки зависимостей можно повторить запуск через **Re-run failed jobs**; повторение не исправляет ошибку в коде. [Справка по повторному запуску](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs).

## Что уже проверено, а что предстоит

На 30.09.2026 локально проверены frontend: чистая установка, сборка и **11 тестов**; backend: restore, Release-сборка без предупреждений и **13 тестов**. Оба YAML прошли actionlint 1.7.12. Использованы Node 24.19.0, npm 12.0.2, .NET SDK 10.0.401 на Windows.

Это результаты CI-веток. Дополнительные изменения каталога из незавершённой задачи Compose сюда не включены. Факт успешного запуска на GitHub и приёмки Клима нужно подтвердить отдельно после ручного создания PR; не выдавайте локальные результаты за эти проверки.
